# Plan for #2: Reject CO2 values outside 0 to 500 g/km

## Goal
- Users sending `co2GramsPerKm` outside 0..500 get `400` with `details: ["co2GramsPerKm must be between 0 and 500"]`; 0 and 500 remain valid. Existing valid-run behavior stays unchanged.

## Dependencies (confirmed / plausible / open), each with change: yes | no
- confirmed: `src/runs.ts::validateNewRun` — add numeric range guard and boundary acceptance; change: yes
- confirmed: `src/app.ts::createApp` — `ValidationError` is already translated to HTTP 400 `{ error, details }`; change: no
- confirmed: `test/app.test.ts::runs api` — add below-min, above-max, and boundary tests; change: yes
- plausible: `public/index.html::new-run` — client submits numeric input; verify whether UI should also block invalid values before POST; change: no
- open: `README.md`, `src/config.ts`, `k8s/configmap.yaml` — no env-var or API-doc change expected; verify against the contract; change: no

## Tests
- `test/app.test.ts`: reject `< 0`, reject `> 500`, accept `0` and `500`.

## Environment contract
- No new or changed environment variables; `src/config.ts` and `k8s/configmap.yaml` remain unchanged.

## Risks
- Wrong range logic or error text breaks the API contract and unit tests.
- Boundary values could be rejected by mistake, or invalid payloads could still pass validation.
- Pipeline risk is low: unit tests are the main gate; rollout/stability/smoke/browser should stay green unless the route contract changes.
